Now what?

You shipped v1.

Every week of this program added a new capability to your stack — connectors, browser actions, system prompts, code. Last week you used all of it to build something real. The build was the easy part.

The harder part — and the part most people skip — is what comes after. v1 is a draft. Drafts get edited. The tools that survive aren't the ones that launched the strongest. They're the ones whose owners kept finding the next thing to fix.

This week is about that loop. You'll use four lenses to look at the tool you built last week — each one shows you something the others can't. Then you'll pick the most painful things you find and ship at least three improvements.

Not a backlog. Not a roadmap. Three or more improvements. Shipped.

The four lenses

You'll use four different lenses to find what to improve, spending roughly 15 minutes on each. Each one surfaces things the others can't. Capture every insight as you go — we'll set up the tool for that right after this section. If a lens turns up nothing, log that too and move on. Don't fake findings.

  • 1
    Self feedback.
    Open your tool. Do the workflow it was built for — not a demo, the real thing. What annoyed you in the first 60 seconds? What did you have to mentally translate or work around? Trust your own annoyance — if it bugs you, it bugs everyone else worse.
  • 2
    User feedback.
    Send it to one colleague (the actual person you built it for, if not you). Ask one question: "What's the first thing you tried, and where did you get stuck?" Don't lead. Don't follow up with explanations. Read what they actually wrote.
  • 3
    Code review.
    Open Claude Code on your repo. Ask something like: "You are the most senior engineer at ATN. Review this codebase as if it's about to be used in production. What's fragile? What will break under unexpected input? What's lazy? Be brutal." This is the W6 self-review you skipped. Take the harshest finding seriously.
  • 4
    Market research.
    Spend 15 minutes with a tool you admire that solves a similar problem. A real competitor counts, but cross-domain is better — Linear, Superhuman, Notion, Stripe Dashboard, Things. What's one move they make that you'd steal? Screenshot it, drop it into Claude, ask: "how would I apply this pattern to my tool?"
Your first command: an idea capturer

You'll surface five to fifteen insights across those lenses. Capturing them in flow — without breaking concentration to open files or fight CLAUDE.md formatting — is exactly the kind of repeated micro-task that custom commands were made for. So before you use the lenses, you're going to build one.

A Claude Code command, at its core, is a saved prompt. When you type /name, Claude runs whatever's stored in .claude/commands/name.md, replacing the $ARGUMENTS token with whatever you typed after the slash. That's the whole concept — you build them once, you use them forever.

The one we're building is /idea. It appends entries to a new IDEAS.md file (keeping CLAUDE.md clean for stable project context, where it belongs).

Setup is one prompt. Open Claude Code in your tool's repo and paste this:

Set up a custom slash command called /idea in this repo.

It should:
- Append entries to an IDEAS.md file at the project root
  (create the file if it doesn't exist)
- Format each entry as a bullet:
  "- [Lens] insight text (severity)"
  example: "- [Code] N+1 query in dashboard route (high)"
  where:
  - Lens is one of: Self, User, Code, Market
  - severity is one of: low, med, high
- Use $ARGUMENTS to capture whatever I type after /idea

Behavior rules for the command:
- If the input doesn't include a lens label in [brackets],
  the command should STOP and ask which lens it came from
  before appending. The lens is required.
- If the input doesn't include a severity, default to (med)
  without asking.

Make sure the .claude/commands/ folder exists (create it if not),
then create idea.md inside with the right prompt.

Claude handles the rest — folder creation, file creation, command registration. Once it's done, test it yourself by typing:

/idea [Self] Empty state on first load is confusing (high)

If a new line lands in IDEAS.md in the right format, the command is working. From now on, every insight is one line away.

The command is yours to keep. Same pattern works for anything else you find yourself doing repeatedly: /triage, /note, /standup. Each one is a single markdown file in .claude/commands/.

Then ship 3+ improvements

By the end of the four lenses, you'll have a stack of insights in IDEAS.md. Pick at least three and ship them.

Three small improvements, not one big one. Sequencing is the muscle: a small fix that ships beats a perfect one that doesn't, and three small improvements practice the iteration loop better than one big push. Each one should be small enough to describe in a single sentence.

Pick the most painful insights, not the easiest. Choosing under pressure is product judgment — that's what this lesson is building.

If a lens reveals your tool is the wrong shape entirely — that's a valid finding too. Note it in your log, decide what you'd do, and ship something fixable for this week.

Why this matters

You wrote software last week. That makes you responsible for it. Most personal software dies in the first month not because it was built badly, but because nobody came back to it. The discipline that distinguishes people who ship once from people who ship forever is small: come back, pay attention, log what you find, ship the next fix, repeat.

The four lenses are the inputs. The log is the memory. Shipping is the muscle. You're learning to use the loop — the loop you'll use on every tool you build from here forward.
